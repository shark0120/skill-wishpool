# publish-gate

## 為什麼要閘門

公開發佈是**單向門**。密鑰進了 git 歷史就洗不掉;誇大的數字被第一個測的人拆穿,信任就沒了;
安裝腳本的漏洞會傷到信任你的人。

閘門的價值不在「通過」,在**擋下來**。實例:一次閘門擋下了安裝器的殼碼注入
(未加引號 heredoc → 持久化 RCE),以及網站上「安裝器做了什麼」與腳本實際行為不符
—— 而那個區塊存在的唯一目的就是讓人敢把指令貼進有 shell 權限的 AI agent。

## 鐵律

1. **四個面向平行、獨立、唯讀。** 稽核員不修東西 —— 修的人和查的人分開。
2. **任一 critical/high → 不推。** 沒有「先推再修」。
3. **稽核員不能只讀摘要,要讀程式碼。** 「宣稱已修」不算修。
4. **驗證修復要用「重新植入缺陷」**:把 bug 放回去,確認測試真的會紅。綠燈不代表測試有效。

## 四個面向

### 1. 洩密
掃全部檔案**加上 git 歷史**(內容乾淨但 commit metadata 有真實 email 也算失敗):
- `sk-[A-Za-z0-9_-]{12,}`、`AIza…`、`ya29.`、`gh[pous]_`、`github_pat_`、`AKIA…`、`xox[baprs]-`
- bcrypt/argon(`$2[aby]$`、`$argon2`)、`BEGIN … PRIVATE KEY`
- 伺服器 IP、雲端專案 ID、機器名、絕對路徑(含使用者名)
- 帳號 email(作者聯絡信箱可能是刻意的 → 標 low 讓擁有者決定)
- **`git log --format='%an|%ae'`** 確認沒有真實個人 email
- **實測** `.gitignore`:`git check-ignore -v` 對每個敏感路徑跑一遍,不要只看檔案內容

自我標示的測試假資料(`sk-...-not-a-real-key`、`AIzaSyFAKEfake…`)不算。

### 2. 資安
以「攻擊者 + 不懂技術的使用者」雙視角讀**實際程式碼**:
- 安裝腳本:命令注入、未加引號展開、eval/source 攻擊者可控資料、寫到 `$HOME` 外、
  覆蓋使用者既有設定、root 拒絕可否繞過、失敗卻回報成功、解除安裝變數為空時刪過頭
- 服務:配額 race(檢查與扣款之間有 await)、串流用量事後才計費導致超支、
  全域上限是「花之前擋」還是「花完才看到」、SQL 是否全參數化、
  代理是否會把內部憑證回傳、hop-by-hop 標頭注入、管理端點是否對外
- 部署:有沒有服務搶佔 80/443、容器 UID 與映像烙印是否一致、healthcheck 路徑是否真的存在、
  加固腳本會不會把操作者鎖在門外、sshd drop-in 命名順序(first-wins,`99-` 會被 `50-cloud-init` 蓋過)

### 3. 誠實性
以「Hacker News 上想抓包你的資深工程師」視角:
- 每個數字都要在**授權證據清單**裡;超出範圍的一律刪除或改成定性描述
- 數字的**限定詞不能掉**(「99.5% 命中」vs「暖輪次 token 加權 99.53%,冷輪次 0%」)
- 「已驗證」和「推論」要分開(機制在原始碼確認 ≠ 效果數字量測過)
- 沒有基準對照就不能宣稱改善
- 限制揭露要**視覺上同等顯眼**,不是塞在頁尾小字 —— 讀 CSS 判斷,不要只看有沒有寫
- 第三方專案的**授權與歸屬要正確**(查它的 LICENSE,不要猜)
- 文件之間互相矛盾 = 高風險
- **最致命的一項**:如果頁面聲稱「這個腳本會做 X」,逐行讀腳本比對。
  不符 = critical,因為那正是讓人放心執行的依據。

### 4. UI / 無障礙(有網頁時)
用程式量測,不要用眼睛判斷:
- 零外部資源(CSP/離線/隱私都靠這個)
- inline script 的 SHA256 與 CSP 宣告一致(不一致 = 上線後整頁功能被擋 = critical)
- 標籤配對、重複 id、錨點可解析、`getElementById` 目標存在
- WCAG AA 對比 **兩個主題都要**,回報最低值
- 鍵盤可操作、焦點可見、`aria-live`、`prefers-reduced-motion`
- 360px 無橫向捲動(寬內容在自己的容器裡捲)
- 失敗時**不得渲染假數字**(fetch 失敗要顯示「未知」,而不是編一個)

## 輸出格式

每個面向回傳:
```json
{"publishable": true|false,
 "blocking_issues": [{"severity":"critical|high|medium|low",
                      "file":"...", "issue":"...", "evidence":"file:line + 實際內容",
                      "fix":"..."}],
 "summary": "..."}
```

**閘門判定**:四項全部 `publishable: true` 才放行。

## 擋下來之後

1. 修復軌和稽核軌分開,不要同一個代理自己修自己驗。
2. 修完**重跑該面向的稽核**,並要求它自己驗證修復,而不是相信宣稱。
3. 修復期間如果別的軌道正在寫同一批檔案,先排序,不要並行寫同檔。

## 安全界

- 稽核員**唯讀**:不建立、不修改、不刪除任何檔案。
- 不因為「趕時間」降級門檻。時程壓力是最常見的失守原因。
- 擋下時要說清楚**為什麼**與**怎麼修**,不要只丟一個 false。
- 發佈本身需要使用者明確同意 —— 閘門通過**不等於**授權推送。
