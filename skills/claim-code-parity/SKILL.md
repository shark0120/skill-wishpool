# claim-code-parity

## 為什麼這件事比它看起來重要

有一類文件不是「說明」,是**信任依據**:

- 「這個安裝腳本會做什麼」→ 使用者據此決定要不要把指令貼進有 shell 權限的 AI agent
- 「我們只記錄 metadata」→ 使用者據此決定要不要傳敏感 prompt
- 「不會修改你既有的設定」→ 使用者據此決定敢不敢在正式機器上跑

**這類陳述錯了,不是文件過期,是欺騙**(即使完全無心)。而且一旦被抓到一處,
整份文件的可信度歸零 —— 讀者會合理推論其他地方也不能信。

## 鐵律

1. **以程式碼為準,改文件。** 不要為了維持文案而改程式,除非程式本來就錯。
2. **列舉式陳述最危險。**「就是這四個,沒有別的」是可證偽的;「主要包含」不是。
   要嘛數字精確,要嘛不要給數字。
3. **引用行號會被查。** 引錯範圍比不引更糟 —— 看起來像刻意挑選。
4. **沒有對應程式碼的句子就刪掉。** 不要改成模糊版本蒙混。

## 方法

### 1. 找出信任依據段落

優先順序:安裝/執行腳本的說明 > 隱私與資料處理 > 安全性宣稱 > 效能數字 > 功能列表。

### 2. 建對照表(一句一列)

| 文件的話 | 對應程式碼 | 相符? |
|---|---|---|
| 「寫入四個環境變數」 | `install.sh:1098,1104-1107,1115-1117,1124` | ❌ 實際 **11 個** |
| 「找出你的 shell profile」 | 找不到;`:30,451,1260,1316` 明說**不碰** | ❌ 完全沒這行為 |
| 「不需要 sudo」 | `:refuse_root()` | ✅ |

**每一句都要有一列。** 沒有對應程式碼的那些,就是你要刪的。

### 3. 逐項驗證,不要用讀的

```bash
# 宣稱寫了哪些環境變數 → 真的抓出來數
python - <<'EOF'
import re, pathlib
t = pathlib.Path("install.sh").read_text()
# 找出實際產生設定檔的區段,列舉所有 export
for m in re.finditer(r"^\s*export\s+([A-Z0-9_ ]+)", t, re.M):
    print(m.group(1))
EOF

# 宣稱不碰某檔 → 搜尋所有寫入路徑
grep -nE "bashrc|zshrc|profile|>>|write_file|tee" install.sh

# 宣稱只記 metadata → 讀 logging 呼叫,看有沒有帶 body/prompt
grep -nE "log\.|logger\.|print\(" gateway/*.py | grep -iE "body|prompt|content|message"
```

### 4. 特別檢查這三種

**列舉不完整** —— 最常見。數量寫死了,程式卻多做了幾件事。
陷阱:引用的行號範圍剛好只涵蓋你數到的那些,漏掉範圍外的。**引用範圍要涵蓋整個產生區段。**

**行為描述與程式相反** —— 「會找出/修改 X」但程式明確拒絕碰 X。
通常是文案先寫、程式後改,沒回頭同步。

**頁面自我矛盾** —— 頂部說「每個數字都可以自己重現」,350 行後說「這個數字是推論,未量測」。
單獨看每一段都沒錯,合起來就是假話。**全文搜尋同一主張的所有出現位置。**

### 5. 留下可重驗的紀錄

把對照表寫進 repo(例如 `docs/CLAIM_PARITY.md`),下一個人才能重驗,
而不是重新從零比對。

## 修完之後

- 改的是**文件**還是**程式**?寫清楚理由。
- 有沒有加測試防止再退化?(例如斷言頁面上的變數清單與腳本抓出來的一致)
- 精確數字最好由程式產生,不要手寫 —— 手寫的必然會過期。

## 反模式

- 把「四個」改成「一些」來規避 —— 讀者要的是精確,模糊化等於承認你不知道。
- 只修被抓到的那一處,不搜尋同類陳述。
- 用 commit message 宣稱已修,但沒有重新逐句比對。
- 引用行號卻沒實際打開那幾行看。

## 安全界

- 本 skill 預設**唯讀比對 + 產出修正建議**;要動檔案前先給對照表。
- 發現隱私或安全宣稱不實時,**先回報再改** —— 那可能牽涉已經發生的使用者風險,
  不只是文案問題。
- 不要為了讓文案成立而放寬程式的安全檢查。
